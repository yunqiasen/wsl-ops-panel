# CF 由面板按需托管，与项目运行分开

2026-10-20 的需求对齐：大多数项目用不上 CF，需要时开启，用完关闭。现有方案以项目自带脚本作为接入条件，导致新发现的项目即使已经运行，CF 按钮仍可能置灰；本轮选择由面板按需管理隧道，而非要求每个项目准备专属脚本。

用户已于 2026-10-20 回复“可以，下一步”，批准本记录的范围并进入规格编写。随后用户对完整规格回复“进入”，已批准规格范围内实现。

## 决定

- 范围为 Docker / Project 的附属访问能力，沿用已有项目发现与分类；其余模块职责保持原样。
- 默认关闭。扫描到新项目时仅识别项目；隧道配置和运行资源在用户点击“开启 CF”后按需创建。
- 开启时识别、核验项目实际入口；多个有效候选入口由用户选择。缺少有效入口时给出具体原因，保留本地项目现状。
- 关闭仅停止对应项目的隧道，本地项目继续运行。再次开启复用已保存的选择，并重新核验入口。
- 隧道资源由面板统一管理，业务项目文件保持原样；常驻隧道与任务中心的短时操作分开。
- 具备 CF 能力、用户开关、实际运行状态分别表达；历史域名文件只作线索，当前网址以实际核验为准。
- 现有外部脚本与隧道保留原归属，兼容路径以明确关联为前提；同名猜测、批量接管以及顺带解除既有停用状态均排除在本轮范围外。

## 取舍

- 继续依赖每项目脚本：改动小，但新项目仍需人工适配，重复保留进程与状态管理逻辑。
- 发现项目后预建全部隧道：省去首次准备，却给大多数用不到 CF 的项目增加配置与后台资源。
- 选择按需统一托管：首次开启需要完成入口核验和准备，但项目文件保持原样，启停与状态规则集中维护。

## 已确认的范围

本期沿用 Quick Tunnel 临时网址，重新建立隧道后网址可能变化；固定域名绑定与新增 CF 开机自启策略另列需求。已有项目发现、自启和通知规则保持原范围。
